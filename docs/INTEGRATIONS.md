Посилання дають точки входу для перевірки. У поточній хмарній сесії проксі повернув HTTP 403 на запити до цих доменів. Перед розробкою кожного адаптера зафіксувати джерело, дату, актуальну версію, доступні можливості для облікового запису, авторизацію, правила пагінації, ліміти, помилки, підтримку тестового середовища та правила повторів. Окремо з'ясувати, чи можна читати опубліковані значення для звірки, чи є версії або умовний запис, і який порядок обробки гарантує платформа. Можливості вважати недоступними до підтвердження.

## Прикладний контракт

Кожен адаптер реалізує лише підтверджені можливості через спільний типізований порт. Порт описує читання замовлень і публікацій, читання цін і запасів та, за підтримки й дозволу, передачу цільових значень. Це внутрішні операції CRM. Адаптер перетворює зовнішні статуси, гроші, час і помилки на доменні типи. Невідомий статус зберігається як вхідний факт і потрапляє в журнал для перевірки. Секрет дістає лише серверний клієнт каналу. Доступи читання й запису розділяти, якщо канал їх підтримує.

CRM визначає внутрішню картку, запас і затверджену ціну. Канал визначає зовнішні ідентифікатори, спостережуваний стан публікації й факти отриманого замовлення. Імпорт зовнішнього залишку використовується для звірки. Зовнішнє замовлення зіставляється за обліковим записом та ID публікації, а SKU використовується тільки для однозначних і підтверджених правил. Розбіжності ціни виявляються окремо від первинної суми вже оформленого замовлення.

## Вхідна синхронізація

1. Використати документований механізм читання. Для polling зберігати курсор у транзакції зі стійким записом сторінки до inbox. Для підтримуваних webhook перевіряти джерело документованим способом, захищатися від повторів і підтверджувати прийом після запису до inbox. Періодично звіряти пропущені зміни через дозволене читання.
2. Дедуплікувати за ID події, а за його відсутності використовувати ключ за обліковим записом, ресурсом, підтвердженою версією або канонічним хешем. Імпорт замовлення додатково захищений унікальним зовнішнім ID. Переходи станів перевіряти за версією чи документованою семантикою. За відсутності надійного порядку читати поточний ресурс, а нерозв'язні конфлікти спрямовувати на ручну звірку.
3. Після зіставлення рядків виконати прикладну команду резервування. За нестачі записати виняток для менеджера. Нова версія замовлення після резервування потребує явної команди зміни резерву. Після відвантаження зміни кількостей проходять через повернення або іншу погоджену операцію.

## Вихідна синхронізація

- Формувати абсолютну цільову кількість або ціну разом із монотонною ревізією для публікації та типу даних. В одній транзакції оновлювати ціль і додавати outbox. Один логічний відправник на публікацію, або на більшу область при пакетних запитах. Перед відправленням перечитувати ціль, пропускати старі завдання, серіалізувати запити й використовувати умовний запис, якщо його гарантує канал. Після відповіді фіксувати підтверджену ревізію й планувати наступну, якщо ціль змінилася.
- Після тайм-ауту результат може бути невідомим. За наявності документованого ключа ідемпотентності повторювати ту саму операцію з тим самим ключем. В інших випадках призупинити чергу для ресурсу й звірити стан через підтримуване читання. Якщо неможливо підтвердити результат або порядок, потрібне ручне рішення. Локальні ревізії самі по собі не гарантують відсутності пізніх записів у каналі.
- Зберігати ліміт за документованою областю дії з розподіленим контролем у Redis. Для 429 враховувати `Retry-After` за наявності, для тимчасових збоїв застосовувати backoff із jitter та обмеженням спроб. Помилки дозволів і валідації переводити в діагностику. Після вичерпання спроб лишати стійкий запис для розбору. Ручний повтор перевіряє актуальну ревізію й права.
- Журнал містить ресурс, напрямок, ревізію, категорію помилки, спробу й кореляційний ID. Відображати час останнього успіху та невідомі або прострочені результати. Звірка порівнює цільову, підтверджену й спостережувану величини. Виправлення виконують ті самі дозволені команди.
- Запис вимкнено за замовчуванням, навіть після підключення реального читання. Перед записом перевіряти режим середовища, явний дозвіл для каналу, облікового запису й операції та чинність погодження. Для активації потрібні окремий дозвіл користувача, попередні контрактні перевірки й тестовий прогін, перегляд цільових змін і план зупинки. Перемикач зупинки перевіряти безпосередньо перед новим запитом. Уже відправлені запити звіряти. Демо-адаптери позначати як симуляцію, без змін зовнішнього стану.

## Імпорт каталогу

API, CSV, Excel (.xlsx) та XML використовують спільний staging. Фіксувати джерело, хеш пакета, версію шаблону та зіставлення полів. Нормалізувати дані, перевіряти обов'язкові значення, типи, дублікати, валюту, SKU та зовнішні ключі. До застосування показувати створення, оновлення й конфлікти по рядках. Записувати ідемпотентними командами порціями з підсумком успішних, відхилених і пропущених рядків. Повтор обробляє той самий пакет без повторних змін. Застарілу пропозицію оновлення відхиляти за версією картки. Імпорт фізичного запасу потребує окремого підтвердження складської операції.

Обмежувати розмір файлів і розпакованих даних, кількість рядків та час обробки. XML без DTD і зовнішніх сутностей, Excel без виконання формул і макросів. Якщо система завантажує фід за URL, дозволяти HTTPS лише на погоджених хостах, перевіряти перенаправлення й блокувати приватні адреси. Захистити експорт звітів від ін'єкцій формул. Сирі файли й payload зберігати обмежений строк у сховищі з контролем доступу.
